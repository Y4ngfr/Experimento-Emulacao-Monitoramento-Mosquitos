#!/usr/bin/env python3
"""
Topologia para Monitoramento de Mosquitos
- 3 Clusters (APs) com 5 sensores cada
- 1 Servidor Central
- 3 Cientistas (clientes)
- Backhaul via Ethernet

Uso:
  python3 topologia.py              # sem visualização gráfica
  python3 topologia.py --plot       # com visualização gráfica
  python3 topologia.py --mqtt       # sobe também o cenário MQTT-SN
  python3 topologia.py --http       # sobe também o cenário HTTP (ramificação)
  python3 topologia.py --coap       # sobe também o cenário CoAP (ramificação)
  python3 topologia.py --mqtt --dash # MQTT + forwarder p/ ThingsBoard (nó "console")

Variáveis de ambiente:
  MININET_SENSORES=N  cria apenas N sensores (padrão 15; reduzido p/ pouca RAM)
"""

"""
Topologia personalizada para monitoramento de mosquitos
USANDO Mininet-wifi DIRETAMENTE (não herda de Topo)

Fases de montagem (importante a ordem):
    1. construir_nos()        -> cria hosts, APs e STAs
    2. add_backhaul_links()   -> links Ethernet (não precisam de wintfs)
    3. configureNodes()       -> cria as interfaces wireless (wintfs)
    4. build()/start()
    5. associar_wifi()        -> associa sensores aos APs APÓS o hostapd
    6. configurar_rede()      -> roteamento e forwarding (pós-start)
"""

# ========== NÓ CONSOLE (nó no netns do host, porta p/ ThingsBoard) ==========
# Host convencional (não-STA/AP), com inNamespace=False: as interfaces
# deste nó são criadas NO NETNS DO HOST (raiz). Como o container roda
# com --network host, o nó "console" equivale a uma interface do SO do
# host. O THINGSBOARD (container docker no host, MQTT publicado em
# 0.0.0.0:1883 do host) fica alcançável de dentro da topologia via o
# endereço 10.10.0.2 deste nó — sem depender de bridge/switch algum.

"""
    Associa sensores aos APs DEPOIS de net.start() (hostapd no ar).
    No ambiente atual (kernel 6.12 + hwsim + netns), associar durante o
    configureNodes travava ("Operation already in progress" / EBUSY),
    pois o connect era emitido antes de o hostapd do AP existir.

    Otimização de tempo: em vez de retries apressados (3x timeout 12s +
    sleep 3s por sensor, que gerava retries desnecessários quando a
    associação levava mais de 3s), faz um iw connect com timeout CURTO e
    depois um POLL PACIENTE de até ~10s no iw link. Assim cada sensor
    paga só o que precisa: ~1-4s saudável, ~10s degradado, sem retry.
"""

"""
    Configura roteamento e forwarding DEPOIS de a rede estar no ar.
    Não pode rodar antes de net.start(): os processos dos nós ainda
    não existem nesse momento.

    Corrige também deficiências do cenário (veths do gw sem IP, bridge
    do AP sem IP, rádio fora da bridge, associação adiada) que faziam o
    pingall falhar neste ambiente.
"""

# Ordem dos addLink do backhaul/cabo: srv(gw-eth0), ap1(gw-eth1),
# ap2(gw-eth2), ap3(gw-eth3), cient1..3(gw-eth4..6).
#
# ===== Desenho de rede (padrão Mininet-WiFi) =====
# O gateway senta NA MESMA SUBNET de cada cluster, via veths ligados
# à bridge do AP: gw-eth1=10.0.1.1/24, gw-eth2=10.0.2.1/24,
# gw-eth3=10.0.3.1/24. O IP "10.0.x.1" (default gw dos sensores) é
# do GATEWAY, não do AP. O AP host fica totalmente fora do caminho
# L3: não tem IP na bridge, não tem rota nem ip_forward; é só uma
# ponte L2 (OVS bridge + NORMAL) entre o rádio e o veth do gw.
#
# Assim o único forwarding L3 necessário é o do gateway (host
# Mininet com ip_forward) e o do srv1 — ambos já comprovados
# funcionando. O kernel do AP (root netns) nunca mais roteia
# pacotes do rádio, eliminando o gargalo que travava o experimento.
